# Bon Appetit

Внутрішня PWA для замовлення їжі на наступний робочий день. Користувач обирає страви з денного меню та локацію отримання. Адміністратор веде каталог страв, публікує меню, керує працівниками та формує звіти для кухні й постачання.

Увесь час у бізнес-правилах рахується в часовому поясі **Europe/Kyiv**.

## Архітектура

Клієнт — односторінковий вебзастосунок (Vite + React 19 + TypeScript). Бекенд і база — **Supabase**: PostgreSQL, Auth, RLS, RPC і Edge Functions.

```
┌─────────────────────────────────────────┐
│  PWA (браузер / встановлений застосунок)│
│  React · Zustand · Service Worker       │
│  Web Push · офлайн-кеш · outbox queue   │
└──────────────────┬──────────────────────┘
                   │ @supabase/supabase-js
                   ▼
┌─────────────────────────────────────────┐
│  Supabase                               │
│  Auth  ·  PostgreSQL + RLS + triggers   │
│  RPC (дедлайни, звіти, кухня, отримання)│
│  Edge: admin-users, send-push (VAPID)   │
└─────────────────────────────────────────┘
```

### Клієнт

| Шар | Призначення |
| --- | --- |
| `src/features` | Екрани: вхід, замовлення, історія, страви, меню, користувачі, звіти |
| `src/services` | Клієнт Supabase, API-запити, синхронізація outbox, Web Push |
| `src/stores` | Zustand: сесія, кеш меню/замовлень, черга офлайн-дій, фільтри адмінки |
| `src/constants` | Словник UI (`dictionary.ts`), дедлайни, кольори |
| `src/utils` | Дати Europe/Kyiv, звіти, мережеві помилки |
| `src/sw.ts` | Service Worker: precache, SPA fallback, push |

Авторизація: логін (мапиться на email Auth) + пароль. Статичний текст інтерфейсу лише зі словника.

### Маршрути

- `/login` — вхід
- `/change-password` — обов’язкова зміна пароля (`must_change_password`)
- `/` — вибір страв (роль `USER`)
- `/history` — історія замовлень (`USER`)
- `/admin/dishes`, `/admin/menu`, `/admin/users`, `/admin/reports` — кабінет `ADMIN`

PWA: `vite-plugin-pwa`, manifest `standalone`, автооновлення SW, кеш оболонки. Меню й замовлення дублюються в `localStorage`. Без мережі користувач може зберегти замовлення в **outbox**; після появи мережі черга відправляється на сервер.

## Структура бази даних

Схема `public`. Доступ до рядків обмежує **Row Level Security**.

### Сутності

**locations** — точки отримання. Зберігається лише назва, без фізичної адреси.

**profiles** — профіль на `auth.users`. Логін, відображуване ім’я (у поточному MVP збігається з логіном), роль `ADMIN` | `USER`, типова локація, блокування, прапорець обов’язкової зміни пароля.

**dishes** — каталог страв: назва, опис, тип прийому їжі, активність.

**daily_menu** — затверджене меню на календарну дату. Одна страва на тип прийому їжі на день (`UNIQUE(date, meal_type)`).

**orders** — одне замовлення на користувача на дату (`UNIQUE(user_id, date)`). Локація отримання, статус, час початку приготування `cooking_started_at`.

**order_items** — позиції замовлення: посилання на рядок `daily_menu`. Не більше однієї позиції на той самий рядок меню в межах замовлення.

**push_subscriptions** — Web Push: `endpoint`, ключі `p256dh` і `auth`.

### Типи прийому їжі

`BREAKFAST` · `LUNCH_FIRST` · `LUNCH_SECOND` · `DINNER`  
(сніданок, обід 1, обід 2, вечеря)

### Статуси замовлення (БД)

| Статус | Значення |
| --- | --- |
| `PENDING` | Очікує приготування |
| `COOKING` | Кухня почала готувати |
| `IN_DELIVERY` | В дорозі |
| `COMPLETED` | Отримання підтверджено |
| `CANCELLED` | Скасовано |

Лише на клієнті (не пишуться в PostgreSQL): `PENDING_SYNC` — збережено офлайн; `SYNC_FAILED_DEADLINE` — сервер відхилив після дедлайну.

### Зв’язки

```
auth.users 1──1 profiles
locations  1──* profiles (default_location)
locations  1──* orders (target_location)
dishes     1──* daily_menu
daily_menu 1──* order_items
profiles   1──* orders ──* order_items
profiles   1──* push_subscriptions
```

### RPC (викликає автентифікований клієнт)

- `check_admin_menu_deadline(date)` / `check_user_order_deadline(date)` — чи відкрите вікно змін
- `get_kitchen_report(date)` — порції за стравою: замовлено й скасовано після старту кухні
- `get_delivery_report(date)` — комплектації по локаціях **без** скасованих замовлень
- `start_kitchen_cooking(date)` — `ADMIN`: усі `PENDING` на дату → `COOKING` + `cooking_started_at`
- `confirm_order_received(order_id)` — власник: `COOKING` / `IN_DELIVERY` → `COMPLETED`
- `cancel_own_order(order_id)` — власник: скасування (`PENDING` лише до дедлайну; після старту кухні — і пізніше)
- `complete_password_change()` — знімає `must_change_password`
- `is_admin` / `is_blocked_user` — допоміжні для RLS

Edge Functions: `admin-users` (створення / оновлення / скидання пароля / видалення, service role), `send-push` (VAPID).

Міграції: `supabase/migrations/`. Початкові дані: `supabase/seed.sql`.

## Ролі та доступи

### USER

- Вхід, обов’язкова зміна пароля після створення або скидання адміністратором.
- Перегляд меню на день, вибір локації, замовлення страв (не більше **однієї порції** на тип прийому їжі).
- Редагування й повторне надсилання, поки статус `PENDING` і не настав дедлайн.
- Після старту кухні: зміна складу заборонена; доступні **Скасувати замовлення** і **Підтвердити отримання**.
- Історія замовлень і статусів.
- Власні push-підписки.
- Офлайн: перегляд кешу; **Замовити** лишається активною і кладе дію в чергу.

Заблокований обліковий запис (`is_blocked`) не входить у систему.

### ADMIN

- Каталог страв (створення, редагування, активність).
- Конструктор денного меню (до дедлайну 10:00 дня D−1).
- Користувачі: створення, роль, локація, блокування, скидання пароля, видалення (не себе).
- Звіти: кухня та постачання, друк, PDF, зведення в буфер.
- Кнопка **Почати приготування** на дату звіту.
- Читає всі замовлення й підписки; пише меню, страви, локації.

Адмін не користується екраном вибору страв працівника.

### RLS (стисло)

| Таблиця | Читання | Запис |
| --- | --- | --- |
| `locations`, `dishes`, `daily_menu` | усі автентифіковані | лише `ADMIN` |
| `profiles` | свої; `ADMIN` — усі | `ADMIN` (і свої обмежені поля за політиками) |
| `orders`, `order_items` | свої; `ADMIN` — усі | свої до обмежень тригерів; `ADMIN` — усі |
| `push_subscriptions` | свої; `ADMIN` — усі | свої |

Тригери додатково блокують зміни меню/замовлень після дедлайну та зміну позицій після старту приготування.

## Логіка дій

### Меню (адмін)

1. Страва живе в каталозі з прив’язкою до типу прийому їжі.
2. На дату D адмін обирає по одній страві на сніданок, обід 1, обід 2, вечерю.
3. Створити або змінити меню на D можна **лише до 10:00** дня D−1 (Kyiv). Після цього дата заблокована.

### Замовлення (користувач)

1. Цільова дата зазвичай **завтра**.
2. Користувач бачить страви з меню (не довільний каталог), вмикає/вимикає порцію, обирає локацію, натискає **Замовити**.
3. Створити, змінити склад або скасувати `PENDING` можна **до 24:00 (23:59) дня D−1**.
4. Одне замовлення на людину на день; у ньому щонайбільше одна позиція на тип прийому їжі.

### Кухня та отримання

1. Адмін у звіті кухні підтверджує старт приготування → замовлення `PENDING` стають `COOKING`.
2. Користувач більше не змінює й не перенадсилає склад.
3. **Підтвердити отримання** → `COMPLETED`.
4. Скасування після старту кухні дозволене; у кухонному звіті ці порції йдуть у стовпець **Скасовано**. **До видачі** = замовлено − скасовано.
5. Стовпець **Страва** в звіті кухні береться з **затвердженого меню** на дату, а не зі списку фактичних замовлень. Категорії завжди: сніданок, обід 1, обід 2, вечеря (нулі, якщо ніхто не замовив).
6. Звіт **Постачання**: кількість страв і комплектів по локаціях **уже без скасованих** замовлень, без окремого стовпця скасувань. Усі локації в таблиці, навіть з нулями.

### Офлайн (користувач)

1. Оболонка PWA й останні меню/замовлення доступні з кешу.
2. Невдала відправка через відсутність мережі → запис у `syncQueue` (`CREATE_ORDER` / `CANCEL_ORDER`), статус **Збережено офлайн**.
3. Подія `online` проходить чергу й пише в Supabase; успіх → `PENDING`.
4. Якщо мережа з’явилась після 24:00 D−1 і база відхилила запит → **Не вдалося надіслати: дедлайн минув**.

### Сповіщення

- Нагадування користувачу замовити до 24:00.
- Нагадування адміну опублікувати меню до 10:00.
- Зміна статусу на `IN_DELIVERY` (системний push).

## Бізнес-логіка (інваріанти)

1. **Час** — лише Europe/Kyiv, у тому числі на сервері (тригери / RPC).
2. **Дедлайн меню:** зміни `daily_menu` на дату D до 10:00 дня D−1.
3. **Дедлайн замовлення:** створення / зміна / скасування `PENDING` на дату D до кінця дня D−1.
4. **Порція:** максимум 1 на тип прийому їжі на користувача на день.
5. **Меню дня:** максимум 1 страва на тип прийому їжі.
6. **Одне замовлення** на пару користувач + дата.
7. **Локація** — назва точки видачі, не адреса.
8. **Перший пароль** задає адмін; до зміни пароля основний функціонал закритий.
9. Після **старту кухні** склад замовлення незмінний; скасування фіксується окремо для кухні; постачання бачить лише актуальні (не скасовані) комплекти.
10. Заблокований користувач не працює в системі.

## Запуск

```bash
npm install
cp .env.example .env   # URL проєкту без суфікса /rest/v1/, anon key, VAPID
npm run dev
```

Збірка: `npm run build`. Міграції застосовуйте до проєкту Supabase в хронологічному порядку з `supabase/migrations/`. Після міграцій виконайте `supabase/seed.sql`, якщо потрібні тестові дані.

### Тестові облікові дані (Seed Data)

Після `seed.sql` доступний обліковий запис адміністратора:

| Логін | Пароль | Роль |
| --- | --- | --- |
| `admin` | `admin123` | `ADMIN` |

У seed для цього акаунта `must_change_password = false`, тож після входу одразу відкривається кабінет адміна. Інші seed-користувачі (наприклад `ivan`) описані в `supabase/seed.sql`.

## Змінні оточення

Клієнт збирається з префіксом `VITE_`. Секрети з привилеями не повинні потрапляти у фронтенд і в Vercel як `VITE_*`.

### Vercel (фронтенд)

Задайте в налаштуваннях проєкту Vercel (Production / Preview):

| Змінна | Навіщо |
| --- | --- |
| `VITE_SUPABASE_URL` | Корінь проєкту, наприклад `https://xxxx.supabase.co` (без `/rest/v1/`) |
| `VITE_SUPABASE_ANON_KEY` | Публічний anon-ключ Supabase |
| `VITE_VAPID_PUBLIC_KEY` | Публічний VAPID для підписки на Web Push у браузері |

Після зміни `VITE_*` потрібна нова збірка.

### Supabase Secrets (Edge Functions)

Лише в секретах проєкту Supabase (Dashboard → Edge Functions → Secrets або CLI). **Не** додавайте їх у Vercel і **не** префіксуйте `VITE_`.

| Змінна | Навіщо |
| --- | --- |
| `SUPABASE_SERVICE_ROLE_KEY` | Service role для `send-push` і `admin-users` (повний доступ до Auth/БД) |
| `VAPID_PRIVATE_KEY` | Приватний VAPID для підпису Web Push |
| `VAPID_PUBLIC_KEY` | Той самий публічний ключ, що й `VITE_VAPID_PUBLIC_KEY` (його читає `send-push`) |
| `VAPID_SUBJECT` | Необов’язково; за замовчуванням `mailto:admin@bon-appetit.local` |

`SUPABASE_URL` у хмарних функціях зазвичай уже доступний від платформи.

## Деплой на Vercel

У корені репозиторію є `vercel.json` з rewrite усіх шляхів на `index.html`:

```json
{
  "rewrites": [
    { "source": "/(.*)", "destination": "/index.html" }
  ]
}
```

Це обов’язково для SPA. Без цього правила на чистому акаунті Vercel перше оновлення сторінки адмінки (`/admin/menu`, `/admin/reports` тощо) поверне **404 NOT_FOUND**.

Команди збірки на Vercel: Install `npm install`, Build `npm run build`, Output `dist`.

## Деплой Edge Functions і секретів VAPID

Потрібен [Supabase CLI](https://supabase.com/docs/guides/cli). З кореня репозиторію:

```bash
npx supabase login
npx supabase link --project-ref YOUR_PROJECT_REF

npx supabase secrets set ^
  VAPID_PUBLIC_KEY="YOUR_VAPID_PUBLIC_KEY" ^
  VAPID_PRIVATE_KEY="YOUR_VAPID_PRIVATE_KEY" ^
  VAPID_SUBJECT="mailto:admin@bon-appetit.local"
```

На macOS / Linux замість `^` використовуйте `\` на кінці рядка або передайте змінні в одному рядку:

```bash
npx supabase secrets set \
  VAPID_PUBLIC_KEY="YOUR_VAPID_PUBLIC_KEY" \
  VAPID_PRIVATE_KEY="YOUR_VAPID_PRIVATE_KEY" \
  VAPID_SUBJECT="mailto:admin@bon-appetit.local"
```

Публікація функції відправки push:

```bash
npx supabase functions deploy send-push
```

`SUPABASE_SERVICE_ROLE_KEY` у hosted Edge Functions зазвичай підставляється платформою. Якщо виклик функції падає на відсутній ключ — додайте його так само через `npx supabase secrets set SUPABASE_SERVICE_ROLE_KEY="..."`.
